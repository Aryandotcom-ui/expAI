# TGN-Trace

TGN-Trace is an investigation layer around a trained Temporal Graph Network (TGN). You pick one
prediction (a link `u → v` at time `t`) and it shows you which past events that prediction
depends on.

- **Correct replay.** You can delete past events and replay history the way the model would
  have seen it: node memory, pending messages and the temporal neighborhood are all
  recomputed, and the original batch boundaries are kept.
- **Explanation checks.** It tests whether an explainer's ranking agrees with the actual
  intervention effect.

**Claim boundary.** We do **not** claim better fraud (or link) detection. The contribution is
correct, memory-aware counterfactual replay, explanation checks against that replay, and an
inspectable UI.

> **Status of the numbers in this repo.** The build environment could not download the
> Wikipedia JODIE data (snap.stanford.edu was unreachable). Every number in `results/` and
> `figures/` was therefore measured on **`synthwiki`**, a synthetic stand-in with Wikipedia's
> schema, generated by `synthetic/generate.py`. They are **not** Wikipedia results. The code is
> dataset-agnostic and defaults to Wikipedia; see [Run on Wikipedia](#run-on-wikipedia).

## Results on `synthwiki` (measured; not Wikipedia)

All numbers come from `results/synthwiki/summary.json` and the files it points to, produced by
the commands below on 4 CPU cores with no GPU. The stand-in has 80,000 events, 6,721 nodes and
400 batches of 200; the test region starts at batch 340.

**E1 Baseline.**

| Measure | Test AP | Test AUC |
|---|---|---|
| Our baseline pass (repo-style mean over batches) | 0.9316 | 0.9087 |
| Repo protocol (training log) | 0.9324 | 0.9102 |

80.4% of test events score ≥ 0.5.

**E3 Replay correctness.**
- Checkpointed vs full replay on 48 (target, removal) pairs covering single and 3-event
  removals, 0–277 batches back: max |error| **0.0** (bitwise identical).
- Stage 1: an empty removal reproduces the baseline exactly, and nothing leaks between calls.
- Two provably unreachable events give delta = 0.0.
- Removing u's most recent event changed the score for 15 of 15 targets. The other 5 of the 20
  sampled targets had no event of u among their K candidates.

**E4 Replay latency** (`figures/synthwiki/latency_vs_distance.png`):

| Replay | Median | IQR |
|---|---|---|
| Full replay | 2.07 s | 1.94–2.19 s |
| Checkpointed replay (C=10, disk checkpoints only) | 0.22 s | 0.19–0.35 s |
| **Speed-up, as measured** | **9.2×** | 5.7–11.4× |

- Median removal distance: 1 batch (IQR 1–8.75).
- Removals more than 50 batches back restore one of the sparse checkpoints (every 25 batches),
  so the speed-up shrinks with distance.
- Before the fast state-advance path (see below), full replay took 32 s and the speed-up was
  38×, with a dense-only checkpoint layout; see `results/synthwiki/replay_bench_dense_only.csv`.

**E2 Explainers vs brute force** (100 test targets with baseline ≥ 0.5, K=20;
`figures/synthwiki/precision_at_k.png`):

| | recency | greedy | CoDy (exact replay) |
|---|---|---|---|
| precision@1 vs brute-force top-1 | 0.41 | 1.00* | 0.60 |
| precision@3 vs brute-force top-3 | 0.44 | 0.75 | 0.57 |
| precision@5 vs brute-force top-5 | 0.46 | 0.70 | 0.51 |
| recall@5 of relevant events (Δ ≤ −τ; mean 4.7 per target) | 0.56 | 0.74 | 0.62 |
| counterfactual success (score < 0.5) | – | 35% (set ≤ 5) | 35% (no size cap) |
| mean set size when successful | – | 2.2 | 3.6 |
| model evaluations per target (mean) | 0 | 72.9 | 56.1 |

\* Greedy's first step evaluates every single removal, so its top-1 *is* the brute-force top-1
by construction. Greedy and CoDy both succeed on 31 targets. Wall-clock runtimes of greedy and
CoDy depend on replays cached in the same process, so compare them by model evaluations.

**E5 Verification** (same 100 targets; τ = 0.001 chosen on 20 validation targets;
`figures/synthwiki/agreement_vs_null.png`):

| | recency | greedy | CoDy |
|---|---|---|---|
| median Spearman(importance, −Δ) | 0.07 | 0.61 | 0.13 |
| median null percentile | 62 | 99.7 | 69 |
| targets with null percentile ≥ 95 | 26% | 86% | 30% |
| flags C / D / I | 80 / 14 / 6 | 78 / 16 / 6 | 80 / 14 / 6 |

(C / D / I = CONSISTENT / DISAGREEMENT / INSUFFICIENT.)

- **τ** sits at its floor. The 95th percentile of control removals (recent events touching
  neither u nor v) is 8e-6.
- At τ = 0.001, 46% of candidate removals clear it, so most targets come out CONSISTENT.
  `summary.json` → `flag_sensitivity_to_tau` shows the distribution at τ = 0.005 / 0.01 / 0.02
  (for recency: 52/31/17, 39/33/28, 27/37/36). That table is a sensitivity check only; τ is not
  re-chosen on test.
- **Signal C (linear estimate)** tracks B closely: Spearman 0.97, median |B − C| = 6e-8, p90
  1.1e-3. Using C instead of B would change 14 of 300 flags.
  - Single removals mostly act through the **neighborhood, not memory**. An event in the
    target's own batch has, by construction, a memory term of exactly 0 (537 of 1990 single
    removals).
  - Removals 1 batch back still have a memory term of exactly 0 in 83% of cases. The "last"
    message aggregator keeps only a node's newest pending message, so removing an older one
    changes nothing.
  - Where memory does change (646 of 1990), the first-order memory term has median relative
    error 14% (p90 95%) and the right sign 97% of the time.

**What these numbers say.**
- On this model, the cheap recency heuristic agrees with true single-event influence only
  slightly better than chance.
- A replay-driven greedy search finds counterfactual sets of 1–5 events for a third of targets.
- CoDy's search, run on exact replay, is comparable in success but less aligned with
  single-event influence.
- Single-event explanations miss interactions.
  - The largest single-event |Δ| per target has a median of 0.038.
  - The greedy set of up to 5 events lowers the score by a median 0.17 (IQR 0.045–0.47).
  - That is a median 2.9× the largest single effect (`set_vs_single` in `summary.json`).

## How replay is made fast (and kept exact)

- **Disk checkpoints.** The state at the start of every 10th batch over the test region and the
  50 batches before it, plus every 25th batch earlier in the stream.
- **In-RAM prefix states.** While one target is being explained, exact baseline states at each
  batch boundary of its window are kept in memory. Before the earliest removed event nothing
  differs from the baseline, so a removal replays only from its own batch.
- **Fast state advance.** With the default TGN flags (memory updated at batch start, messages
  built from raw memory), the embedding computation never affects the state. `advance_state`
  therefore applies only the memory update, clears the messages and stores the new raw
  messages. This is 14× faster per batch. `tests/test_stage0.py` checks that the resulting
  state is bitwise identical to `TGN.compute_temporal_embeddings`. Set
  `TGN_TRACE_FAST_ADVANCE=0` to use the model's own path.

## Baseline state definition

Our baseline is built in four steps:

1. Reset memory.
2. Run one clean, deterministic, `no_grad`, eval-mode pass of the final checkpoint over the
   **whole stream**: every event, train, then validation, then test.
3. Cut each region into batches of 200, as the training and evaluation loops do. Each event
   keeps its batch id forever.
4. Use the full neighbor finder with most-recent sampling (`uniform=False`). Equal timestamps
   are ordered by `edge_idx`.

This differs slightly from the memory state at the end of training:

- Training skips the edges of held-out "new" nodes.
- Training interleaves gradient steps.
- The repo's test evaluation continues from the memory left after validation.

AP/AUC are reported for **our** pass, using the repo's test negative sampler (seed 2, reset at
the start of the test region). The training log's numbers are printed next to them.

The model state is `(memory.memory, memory.last_update, memory.messages)`.
`Memory.backup_memory()` and `restore_memory()` deep-copy all three; `tests/test_stage0.py`
checks this by mutating the live state in place.

## Demo

1. Start the API with `uvicorn tgn_trace.api.main:app --port 8000`, then open
   http://localhost:8000/.
2. Pick a target. Targets marked ✓ have stored verification. The candidate table shows each
   event's replay delta (brute force). The timeline and the graph color events by the selected
   explainer's rank.
3. Click an event. The evidence panel shows:
   - its explainer rank (Signal A)
   - its replay delta (Signal B)
   - the linear estimate (Signal C), with its structural and memory terms
   - the target's flag and the reason for it
4. Click **Remove selected** for one or more events, then **Replay**. The dashed purple card is
   the counterfactual ("did not happen"). It shows the baseline vs counterfactual score, any
   class flip, the events replayed, the checkpoint used and the latency.
5. Switch the explainer to greedy or CoDy to see a counterfactual set. Click **Restore** to go
   back.

## Disk usage

State checkpoints hold packed CPU tensors, written every C=10 batches over the test region plus
the 50 batches before it. On `synthwiki` that is 11 files of about 23.6 MB each, about 260 MB in
total. Wikipedia has about 1.4× the nodes and about 2× the test batches, so expect roughly
0.5–0.8 GB. Use `TGN_TRACE_CKPT_EVERY` to trade disk space for replay latency.

See `docs/limitations.md` and `docs/cody_notes.md`.
